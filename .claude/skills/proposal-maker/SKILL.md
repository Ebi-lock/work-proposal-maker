# 企画書・提案書メーカー

決裁者や顧客が「読む価値がある」「承認できる」と判断できる資料を、対話で内容を固めながら PowerPoint で作る。

このスキルで大事なのは次の3つ。
1. **種類に合った型**：企画書（自社で何をやるか）と提案書（相手の課題をどう解決するか）では、主役と構成が違う。さらに提案書は、社外向けか社内向けかで、書き方とチェック項目が変わる。
2. **中身**：雛形の必須項目をすべて埋め、各スライドが論理的につながっていること。
3. **事実**：数字や固有名詞はユーザーの情報か、出典のある公開データだけを使う。資料の数字は判断材料になるため、もっともらしい数字を作ると実害が出る。分からない所は質問するか【要確認】と明記する。

## 使うファイル
| ファイル | いつ読むか |
|---|---|
| `references/kikakusho.md` | 企画書のとき。セクションごとの必須項目・質問例 |
| `references/teiansho.md` | 提案書のとき。社外向け・社内向けの構成と、セクションごとの質問例 |
| `references/checklist.md` | 骨子確認時と生成後。共通・社外向け・社内向け・企画書のチェック項目 |
| `references/schema.md` | JSON を書く前。スライドの種類とデータ形式 |
| `assets/example_kikaku.json` | 商品企画書の完成例 |
| `assets/example_teian_external.json` | 社外向け提案書の完成例 |
| `assets/example_teian_internal.json` | 社内向け提案書の完成例 |
| `scripts/build_deck.py` | JSON から .pptx を生成（python-pptx が必要） |
| `scripts/icons.py` | build_deck.py が使う図形アイコン集（直接読む必要はない。名前の一覧は schema.md） |
| `scripts/preview.sh` | .pptx を PNG にして見た目を確認（macOS ＋ PowerPoint がある場合のみ） |

## デザインルール（ユーザー指定）
- **フォントはメイリオ1種類のみ**。スクリプトが全テキストに設定する（日本語・英数字とも）
- **色はベース・サブ・ポイントの3色**。本文の濃いグレーと背景の白は色数に数えない。淡い背景はこの3色を薄めて作るので、色は増えない
- **1スライド1メッセージ**：各スライドの見出し（message）に、そのスライドの結論を1文（40字前後）で書く。「3C分析」のような項目名だけの見出しにはしない
- **文字を詰め込まない・書き込みすぎない**：決裁者はスライドを「読む」のではなく「見て」判断する。文字で埋まったスライドは、どこが大事か分からず、結局読まれない
  - 箇条書きは1枠3〜4項目、1項目30字程度。1枚の本文は150〜200字が目安（250字を超えるとスクリプトが警告）
  - 文章ではなく要点を書く（「〜することで〜が可能になります」→「〜で〜を削減」）。詳しい説明は口頭か補足資料へ
  - 余白は欠点ではない。枠が空いて見えても、文字を足して埋めない
  - 本文の文字は12pt未満に縮めない。入らないときは文字を削るか、スライドを分ける
- **画像は一部に使う**：シンプルな単色アイコン（図形で描くので3色ルールの中に収まる）を、内容の種類を一目で区別したい所だけに付ける。全項目に付けると、かえって目が散る。ユーザーの手元にある商品写真・画面イメージ・ロゴは、見せた方が早い場面で使う。画像を作ったり、ネットから拾ったりはしない
- **導線を分かりやすくする**：読み手が迷わず、順番どおりに目を動かせるようにする
  - 資料全体：表紙の次に目次（agenda）を置き、話の道筋を先に見せる。右上の現在地バーで「今どこか」が分かる（自動）
  - 1枚の中：見出し（結論）→ 本文（根拠）→ 示唆（だから何か）の順に、上から下へ。横に並べるものは左から右へ、原因 → 結果、課題 → 解決策、現状 → 目指す姿の順にする
  - スライド間：前のスライドの示唆が、次のスライドの見出しにつながるようにする。番号（課題1・課題2…）や矢印で対応関係を示す

## 進め方

### Step 0：種類を確認する（最初に必ず行う）
依頼の文面から推測できても、最初に確認する。種類で構成が大きく変わり、途中で変えると作り直しになるため。

1. **企画書か、提案書か**
   - 企画書：自社の新しい商品・サービス・施策を「やりたい」と社内で通す資料（例：新商品の企画）
   - 提案書：相手の課題に対して解決策を「採用してほしい」と示す資料（例：顧客へのサービス導入提案、上司への業務改善提案）
2. **提案書の場合は、社外向けか、社内向けか**
   - 社外向け：クライアントへの営業提案。相手の課題への共感から入り、実績で信頼を補う
   - 社内向け：上司・決裁者への稟議や改善提案。結論から入り、費用対効果・代替案・リスクで判断材料をそろえる

AskUserQuestion ツールが使える場合は、選択肢で聞く。推測が付く場合は、それを推奨の選択肢として先頭に置く。

確認後、種類に応じた参照ファイルを読む。
- 企画書 → `references/kikakusho.md`
- 提案書 → `references/teiansho.md`（社外向け・社内向けの該当部分）

### Step 1：概要を聞く
すでに分かっていることを話してもらう。一度に聞くのは3〜4問まで。
- **企画書**：どんな商品か／誰向けか／なぜ今か／提出先と提出日／手元の資料
- **社外向け提案書**：提案先の会社名・担当者・役職／先方の課題（ヒアリング内容）／提案する商品・サービス／自社名と担当者／提出日
- **社内向け提案書**：宛先（役職）／何を変えたいか／現状の課題を示す社内データ／おおよその費用／提出日

あわせて、使える画像（商品写真・パッケージ案・画面イメージ・ロゴなど）があるかを聞く。無くてもアイコンで作れるので、無理に用意してもらう必要はない。

資料のファイルやURLがあれば読み込み、各セクションに使える情報を先に拾っておく。ユーザーがすでに話した内容を、もう一度質問しない。

### Step 2：配色を決める（毎回ゼロから質問する）
配色は資料ごとに決める。既定色は持たない。次の3色を質問する。
- **ベース色**：見出し帯・表のヘッダーなど、資料全体の印象を決める主役の色。白文字が読める濃さが必要
- **サブ色**：補助の見出し帯やグラフのバーに使う。ベースと同系色の薄め、または相性の良い色
- **ポイント色**：結論や一番大事な数字だけに使う強調色。全体の5%程度

ユーザーが色を決めていない場合は、イメージを聞いて、それに合う3色の組み合わせを2〜3案、HEXコード付きで提案して選んでもらう。イメージを聞くときの手がかりは次のとおり。
- 社外向け提案書：自社のコーポレートカラー、または提案先のブランドカラー
- 社内向け提案書：社内資料の標準色
- 企画書：商品のイメージ

生成時にスクリプトが白背景での読みやすさを確認し、問題があれば警告を出す。

### Step 3：セクションごとに対話で埋める
参照ファイルの標準構成の順に、1セクションずつ進める。各セクションでは次を行う。
1. これまでの情報から埋められる項目を、**下書きとして見せる**
2. 足りない項目だけを質問する（一度に2〜4問）
3. ユーザーが「分からない」「任せる」と言った場合は、仮案を作って確認をもらう。数字は仮案にせず【要確認】とし、根拠の探し方を提案する（類似実績、公開統計、ヒアリングで聞くべきことなど）
4. 確定したら次へ進む。今どこにいるかを示す（例：「4/9 期待される効果」）

進め方のコツ：
- 前のセクションの結論を、次のセクションの下書きに反映する
  - 企画書：3C → SWOT → As-Is/To-Be → 課題とゴール
  - 提案書：課題 → 解決策 → 効果
- サマリー（提案の概要）は、ほかのセクションが固まってから最後に作る。スライド上の位置は標準構成のまま
- ユーザーが「一気に作って」と言った場合は、それに従う。分かっている情報で全体を下書きし、足りない所に【要確認】を入れて作ってから、まとめて確認する
- 市場データが必要で Web 検索が使える場合は、出典付きで候補を提示し、使うかどうかをユーザーに決めてもらう
- 下書きは最初から短く書く。ユーザーから多くの情報をもらっても、全部をスライドに載せない。結論に効く情報だけを選び、残りは「口頭で補足」「補足資料へ」と伝える
- アイコンは、課題・解決策・効果・手順など、項目の種類が並ぶ所に付ける。どのアイコンにするかは内容から選び、下書きで見せる（schema.md の一覧）

### Step 4：骨子を確認し、チェックする
JSON を作る前に、全スライドの「セクション名｜メッセージ（1文）」を一覧で見せ、ストーリーの確認をもらう。

あわせて `references/checklist.md` で、「共通」と、種類に合ったリストを確認する。
- 企画書 → 「企画書」
- 社外向け提案書 → 「社外向け提案書」
- 社内向け提案書 → 「社内向け提案書」

結果は「OK／要対応」の表で見せる。表記や数字の不一致など自分で直せるものは直してから報告し、事実の確認が必要なものは質問する。
ここで直す方が、スライドを作ってから直すより早い。

### Step 5：生成する
1. `references/schema.md` に従って JSON を作り、作業用の一時ファイルとして保存する
2. 生成する：
   ```bash
   python3 <skill-dir>/scripts/build_deck.py content.json -o "<出力先>/<種類>_<タイトル>_<YYYYMMDD>.pptx"
   ```
   種類は「企画書」または「提案書」。出力先は、ユーザーの指定がなければ現在の作業ディレクトリ。
3. **警告が出たら直して再生成する**
   - 「メッセージが2行」→ 見出しを40字前後に短くする
   - 「はみ出す可能性」→ 文章を短くするか、項目を減らす（文字を小さくして押し込まない）
   - 「本文が約〇字」「箇条書きが〇項目」「〇字を超える項目」→ 書き込みすぎ。要点だけ残して削る。どうしても必要な情報なら、スライドを分ける
   - 「アイコン名は使えません」→ schema.md の一覧の名前に直す
   - 【要確認】の一覧 → 最後にユーザーへ伝える
4. macOS で PowerPoint がある場合は、見た目を確認する：
   ```bash
   bash <skill-dir>/scripts/preview.sh "<pptx>" <作業ディレクトリ>/preview
   ```
   PNG を読み、次を確認して、必要なら JSON を直す。PowerPoint が無ければこの手順は飛ばし、飛ばしたことを伝える。
   - はみ出し・重なり
   - 文字で埋まって見えるスライドがないか（パッと見て、どこが結論か3秒で分かるか）
   - 目の動きが迷わないか（見出し → 本文 → 示唆、左 → 右の順に読めるか）
   - アイコンが内容に合っているか、付けすぎていないか

### Step 6：渡す
次の内容を伝える。
- .pptx の保存場所（フルパス）
- チェックリストで「要対応」のまま残った項目
- 【要確認】が残っている箇所（スライド番号と項目）
- 次にできること（例：「〇〇の数字が分かれば差し替えます」「社内向けに作り替えることもできます」）

修正を頼まれたら JSON を直して再生成する。PowerPoint を直接編集すると、デザインの統一が崩れるため。

## 雛形の構成（概要）
詳しい構成と各スライドの役割は、参照ファイルにある。

**企画書（標準15枚）**：表紙 → 目次 → エグゼクティブサマリー → 背景・現状分析 → 3C分析 → SWOT分析 → As-Is/To-Be → 課題とゴール → ターゲット・コンセプト → 企画内容（6W2H） → 商品戦略（4P） → スケジュール・体制 → 予算・収支計画 → 期待効果とリスク・対策 → ネクストアクション

**社外向け提案書（標準11枚）**：表紙（〇〇御中） → 目次 → 背景・現状の課題 → ご提案の概要 → ご提案内容 → 導入ステップ → 期待される効果 → プラン・費用 → スケジュール・体制 → 会社概要・実績 → まとめ・ネクストアクション

**社内向け提案書（標準12枚）**：表紙（宛先） → 目次 → 提案の概要（結論先） → 背景・現状の課題 → As-Is/To-Be → 提案内容 → 期待される効果 → 費用・投資対効果 → 比較検討した案 → スケジュール・体制 → リスク・関連部署への影響 → 承認のお願い

ユーザーが不要と判断したスライドは外してよい。ただし提案書の必須7要素（タイトル、背景・課題、概要、提案内容、効果、スケジュール・体制・費用、まとめ）は欠かさない。補足が必要なときは bullets で追加する。
